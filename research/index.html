Principles

Architecture is also a model of responsibility. We separate ownership, production and approval so that speed does not quietly remove the controls that make a system trustworthy.

One owner, one system of record

Every critical object has one authoritative owner and one place where its state is maintained. Integrations move data; they do not create competing truths.

Authority stays separate

The component that produces work cannot approve its own production. Permissions, review and release remain explicit decisions.

Test breadth over test count

Exercise contracts, failure paths, permissions and real user journeys. A larger test total is not evidence unless the relevant risks are covered.

AI proposes, people authorize

AI can draft and recommend without granting itself access, approval or release rights. Human review must have enough context and time to catch an error.

Decision gates

Each stage produces evidence for the next decision. A gate can lead to continuation, revision or a stop; passing is never assumed from the amount of code already written.

  1. Discovery

    Inventory workflows, data owners, intended purpose, existing components and unknowns. Establish a baseline before promising an effect.

  2. Foundation

    Define contracts, access boundaries, audit events, fixtures and acceptance tests before connecting production authority.

  3. Shadow mode

    Run beside the existing workflow without autonomous effect. Compare outputs, reconcile data and record overrides, failures and workload.

  4. Consolidation

    Preserve verified capabilities, isolate uncertain components and retire replaced paths against explicit criteria rather than running two systems indefinitely.

  5. Evaluation and scaling

    Review the same measures against baseline. Expand only when safety, quality and use remain within the agreed limits.

Evaluation

We evaluate the sociotechnical system, not only model output or code coverage. Measures are defined before a pilot, versioned with the system and reviewed together so an improvement in one dimension cannot hide harm in another.

DimensionEvidence to collectDecision question
SafetyCritical errors, near misses, overrides and incident severityAre stop conditions absent, and can people still detect failure?
Data qualityCompleteness, provenance, reconciliation differences and unresolved identitiesCan every material output be traced to valid input and an accountable owner?
WorkloadActive handling time, review effort, interruptions and duplicate entryDoes the whole workflow improve without moving hidden work to another role?
AdoptionEligible-use coverage, actual use, abandonment and user-reported trustIs the system used as intended in the real setting?
MaintainabilityChange failure, recovery evidence, dependency risk and test breadthCan the system change without weakening its evidence or controls?

No universal threshold fits every product. The baseline, tolerance, sample and stop rules must be agreed for the specific workflow before results are interpreted.
