Security and data privacy

MR Software builds systems with fail-closed defaults: access starts at zero, consequential changes need evidence and approval, and privileged secrets stay out of the model context. Here is how SAASSY Prison limits delegated work, how we reduce attack risk, and how we shape the system around your field and your customers.

Secure by default

Access starts at zero

No agent, tool or user receives access until it is explicitly granted. Missing approval or missing evidence blocks a governed action, never the other way round.

Human approval

Changes with consequences need approval tied to a specific action, resource and environment. An approval expires and cannot be reused for a different change.

Secrets stay in the vault

Configuration refers to Key Vault names rather than secret values. Privileged secrets stay out of the model context, and governed dispatch grants scoped access only after permission, policy and approval checks.

Tenants are isolated

State and audit events are partitioned per tenant. Only a minimal index of permission id + tenant id is global.

Tamper-evident audit trail

Security decisions and approvals are appended to a separate audit service with a SHA-256 hash chain and verification. If a security-critical audit record cannot be written, the action is refused.

Protected environments

High-risk production changes require explicit owner approval in a protected environment. Merging code is not, by itself, approval to deploy it.

SAASSY Prison: a boundary around delegated work

SAASSY Prison separates what an agent may do, what it must ask about and what it can never change. The model does not police itself: deterministic policy checks sit outside the model and before side effects, so untrusted content cannot redefine the rules.

Inside the prison

Delegated actions the agent may perform autonomously within its granted tenant, tool and task scope. The boundary defines the work; it does not give blanket access.

At the gate

Actions the agent may propose but not execute until a person approves the exact change. Approval is bound to the actor, action, resource, environment, change reference, parameter hash, policy revision and expiry.

Outside the prison

Root policy, privilege escalation, secrets in model context, audit rewriting and break-glass are not agent-writable. An agent cannot expand its own boundary.

The Control Center distinguishes documented policy from enforcement that is actually wired. A policy page alone is not treated as proof that a control is active.

How we reduce attack risk

We combine preventative controls, approval boundaries and evidence that supports detection and investigation. Just as importantly, we record the limits instead of hiding them.

RiskControlImportant limit
Prompt injection and untrusted contentExternal content and model output are untrusted. Deterministic policy checks run outside the model and before side effects; the three Prison zones limit available actions.This limits the potential blast radius. It does not guarantee that prompt injection itself can always be prevented.
Credential misuseOn the governed MCP dispatch path, scoped credential leases are issued only after permission, policy and approval checks. These leases have a five-minute lifetime.Not every credential is short-lived. Existing static credentials still need their own protection and rotation.
Unauthorised production changesApprovals bind a person to the exact proposed change, and high-risk production deployment requires explicit owner approval.Signing in through Cloudflare Access alone proves neither operator authorisation nor backend health.
Audit tampering or audit outageA separate append-only audit service uses internal ingress and a SHA-256 hash chain. Security-critical actions fail closed when their audit record cannot be written.Tamper-evident records support verification and investigation; they do not make every operational failure impossible.
Emergency-path abuseBreak-glass requires human SSO, a requester and two other approvers, and a time-limited window. Agents and service tokens are refused.The exceptional procedure does not replace normal access controls or the need to review what happened.
These controls are designed to reduce risk and limit impact. No system can promise to prevent every attack or data breach. This page describes security design and implemented controls; it is not a live health report.

Data privacy

MR SAAS'y is designed to limit processing to the data needed to run the system: workflow events, permissions, approvals, audit events and agent performance signals.

DataPurposeNote
Workflow eventsTraceable execution and recoveryAppend-only event stream
Permissions & approvalsAccess controlSplit by tenant, audit-logged
Audit eventsRecord of decisionsAppend-only, SHA-256 chained and verified
Agent performance dataRouting and learningAggregated signals rather than raw provider arguments in security records
Security records use identifiers, metadata and hashes instead of raw provider arguments. Privileged secrets stay out of model context. Data needed to execute a workflow is handled within its agreed purpose and access boundaries.

As a company we are bound by the General Data Protection Regulation (GDPR). Processing is limited, tied to a purpose and backed by the necessary technical and organisational measures. Contact us at kontakt@mrsoftware.dk with any questions about data protection.
